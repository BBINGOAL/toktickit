## 1. Sprint Goal

Deliver a fully functional Requester-facing ticketing experience that allows a Development Requester (simulated via a selector) to create IT support tickets, view and search their own tickets, inspect ticket details, and manage permitted file attachments — all backed by a PostgreSQL database, a REST API, and a consistent Zen Green UI that will serve as the reusable design system for future sprints.

---

## 2. Stakeholder Request Interpretation

The IT department needs a professional end-user (Requester) ticketing interface. A Requester must be able to describe a problem by selecting a Category and Related System, setting a requested priority, attaching evidence files, and submitting a ticket. After submission, they must be able to search, filter, and paginate their own ticket list, open a Ticket Detail screen to inspect all fields, and manage attachments (add, download, or soft-remove with a reason). The backend must generate a unique official Ticket Number and prevent cross-Requester data access. Because authentication is out of scope in this sprint, a temporary Development Requester selector simulates the logged-in identity for testing purposes only.

---

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism, not login)
- Create Ticket screen with validation, attachments, and success confirmation
- My Tickets screen with search, filters, sorting, and pagination
- Requester Ticket Detail screen (read-only ticket header)
- Attachment lifecycle: upload, download, and soft-removal with confirmation and reason
- PostgreSQL schema: DevRequester, Ticket, Attachment, Category, RelatedSystem
- REST API supporting all above operations with ownership enforcement
- Zen Green Theme UI and reusable component conventions
- Responsive layout (desktop ≥ 992px, tablet 768–991px, mobile < 768px)
- Seed data: 4 Categories, ≥6 Related Systems, ≥4 active + 1 inactive Dev Requesters

### Excluded
- Authentication: login, logout, passwords, sessions, tokens, role-based access
- IT Staff workflow: dashboard, claim tickets, reassign, change IT Priority
- Ticket collaboration: Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle changes: resolve, close, reopen, cancel (status stays "New")
- Administrator functions: user/role/reference-data management

## 5. Business Rules

| ID | Rule |
|---|---|
| BR-01 | The official Ticket Number is generated by the backend and must be globally unique. Format: `TKT-{YYYY}-{6-digit-sequence}` (e.g., `TKT-2026-000001`). |
| BR-02 | A newly created Ticket begins with Current Status = `NEW`. |
| BR-03 | Lab 2 uses a Development Requester selector instead of real login. The selected identity is for testing only and is NOT authentication. |
| BR-04 | Only active Development Requesters (isActive = true) appear in the selector. Inactive Requesters are excluded. |
| BR-05 | If no Requester is selected, My Tickets, Create Ticket, and Ticket Detail screens are not accessible; the Requester Selection screen is shown instead. |
| BR-06 | A Ticket belongs to the Requester that was selected at the time of creation. Ownership cannot be transferred. |
| BR-07 | A Requester may only view tickets they own. Backend must return 403 Forbidden if a Requester requests another Requester's ticket. |
| BR-08 | Ticket Summary: required; 5–200 characters after trimming whitespace. |
| BR-09 | Ticket Description: required; 10–2000 characters after trimming whitespace. |
| BR-10 | Requested Priority: required; must be one of LOW, MEDIUM, HIGH. |
| BR-11 | Category: required; must reference an active category. |
| BR-12 | Related System: required; must reference an active related system. |
| BR-13 | The Submit button is disabled while a ticket creation request is in flight (busy state) to prevent duplicate submissions. |
| BR-14 | If ticket creation fails, all form values are preserved and an error message is displayed. The Ticket Number is not shown. |
| BR-15 | Allowed attachment types: JPG, JPEG, PNG, WEBP, PDF. |
| BR-16 | Maximum attachment size: 5 MB per file. |
| BR-17 | Maximum active (non-removed) attachments per Ticket: 5. |
| BR-18 | Attachment removal must be implemented as soft removal (isRemoved = true with a timestamp and reason). The file record is retained. |
| BR-19 | A soft-removed attachment remains visible as metadata in the UI but cannot be downloaded or previewed. |
| BR-20 | A soft-removal reason is required; the confirmation dialog shall not allow submission without it. |
| BR-21 | Only the Requester who owns the ticket may remove an attachment on that ticket. |
| BR-22 | If a ticket is created successfully but an attachment upload fails, the ticket is kept and the upload failure is reported separately (compensation: ticket survives). |
| BR-23 | Uploaded filenames are sanitized and stored safely (no path traversal). The original filename is stored as metadata. |
| BR-24 | My Tickets default sort: Created Date descending (newest first). Secondary sort: Ticket Number descending. |
| BR-25 | Permitted My Tickets page sizes: 10, 25, 50. Default: 10. Invalid page or size parameters return an appropriate error. |
| BR-26 | The My Tickets empty state (no tickets) and no-results state (search/filter returns nothing) are presented distinctly. |
| BR-27 | All API errors return a consistent JSON error shape: `{ "error": "<message>" }`. Unexpected server errors must not leak stack traces. |
| BR-28 | In Lab 3, the DevRequester selector will be replaced with secure authentication. The schema must allow a User ID to be added to Ticket without breaking existing data. |

## 6. UI Specification Summary

### Application Shell
- App header: "TokTickIT" branding, My Tickets and Create Ticket navigation, selected Requester name, Change Requester action.
- Primary green `#006B3C` header; white text.

### Development Requester Selection Screen
- Dropdown listing active Requesters only.
- Note: "This is for testing only, not a login screen."
- Note: "Authentication coming in Lab 3."
- On failure to load: clear error state with retry.

### Create Ticket Screen
- System-generated fields (Ticket Number, Ticket Date, Requester) — read-only, distinct background.
- Editable fields: Category, Related System, Priority (dropdowns), Summary (text), Description (textarea), Attachments (file picker).
- Required fields marked with red asterisk (*).
- Inline validation messages below invalid fields.
- Submit button: busy/spinner while processing; disabled during submission.
- Success state: shows generated Ticket Number + link to My Tickets.
- API failure: preserves all form values; shows top-level error message.

### My Tickets Screen
- Table on desktop; card/responsive-table on mobile.
- Columns: Ticket No., Created Date, Summary, Category, Requested Priority, IT Priority, Current Status, Ticket Owner, Last Updated.
- Search bar, filters, Clear Filters, sortable columns, pagination with page-size selector.
- Empty state, no-results state, loading skeleton, and failure state.

### Requester Ticket Detail Screen
- All header fields read-only.
- Attachments section: active and removed items visually differentiated.
- Add Attachment (disabled at 5-attachment limit).
- Download (active only) and Remove (active only, requires reason).
- Back to My Tickets link.

Full details in `docs/lab-02/ui-spec.md`.

## 9. Acceptance Criteria

| ID | Criterion |
|---|---|
| AC-01 | Given valid ticket data, when submitted, then one Ticket is saved, official Ticket Number is displayed in `TKT-{YYYY}-{6 digits}` format. |
| AC-02 | Given no Dev Requester is selected, when the user opens My Tickets or Create Ticket, then the Requester Selection screen is shown. |
| AC-03 | Given Requester B is selected, when Requester A's ticket is requested via API, then 403 Forbidden is returned. |
| AC-04 | Given empty Summary, when submitted, then a field-level error appears below Summary and the API is not called. |
| AC-05 | Given Summary > 200 characters, when submitted, then a field-level error appears and the API is not called. |
| AC-06 | Given a file > 5 MB is selected, when attaching, then an error message is shown and the file is rejected before upload. |
| AC-07 | Given a disallowed file type (e.g., .exe), when attaching, then an error is shown and the file is rejected. |
| AC-08 | Given a Ticket has 5 active attachments, when trying to add another, then Add Attachment is disabled with an explanatory message. |
| AC-09 | Given Requester A's My Tickets is showing, when Requester B is selected, then Requester A's tickets disappear and Requester B's tickets load. |
| AC-10 | Given My Tickets has results, when the Requester searches for a keyword, then only matching tickets are shown with correct pagination. |
| AC-11 | Given My Tickets has results, when a Category filter is applied, then only tickets in that category are shown. |
| AC-12 | Given My Tickets has results, when sorted by Created Date descending, then tickets appear newest first. |
| AC-13 | Given a Requester has no tickets, when My Tickets is opened, then a meaningful empty state message is shown (not an error). |
| AC-14 | Given a search returns no matches, then a no-results state is shown, visually distinct from the empty state. |
| AC-15 | Given a Requester owns a Ticket, when Ticket Detail is opened, then all ticket fields are displayed read-only. |
| AC-16 | Given an active attachment in Ticket Detail, when the Requester clicks Download, then the file is downloaded. |
| AC-17 | Given an active attachment, when soft-removed with a reason, then it is marked removed, no longer downloadable, but still visible as metadata with the reason shown. |
| AC-18 | Given the backend is unreachable, when Create Ticket is submitted, then a safe error message is shown and all form values are preserved. |
| AC-19 | Given the Create Ticket screen at mobile viewport (< 768px), then fields stack vertically, no horizontal scroll, and buttons are touch-friendly. |
| AC-20 | Given an inactive Dev Requester exists in the database, when the selector loads, then the inactive Requester does not appear in the list. |

## 11. Assumptions and Decisions

| # | Decision | Rationale |
|---|---|---|
| D-01 | Ticket Number format: `TKT-{YYYY}-{6-digit-zero-padded-sequence}` | Matches examples in Lab sheet and sample UI screenshots. |
| D-02 | IT Priority is nullable on creation; IT Staff sets it in a later sprint. | IT Staff workflow excluded from Lab 2. |
| D-03 | Selected `requesterId` stored in React context (or localStorage as fallback). Not a session or token. | Avoids auth infrastructure excluded by scope. |
| D-04 | Files stored on server filesystem under `uploads/` with UUID filename. Original filename stored as metadata. | Simple for Lab 2; replaceable with object storage later. |
| D-05 | Soft-removed attachments are never physically deleted from disk in Lab 2. | Simplifies implementation; deletion policy deferred. |
| D-06 | `DevRequester` is separate from a future `User` model. Lab 3 will add `User` and migrate FK. | Keeps Lab 2 clean without blocking Lab 3 upgrade path. |
| D-07 | Page size options: 10, 25, 50. Default: 10. | Practical defaults consistent with common ticketing systems. |
| D-08 | Search covers `ticketNumber` and `summary` (case-insensitive ILIKE). | Most useful quick-lookup fields. |
